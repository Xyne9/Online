# 01 · 原型与接口契约对接可行性判定报告

> **判定对象**：`prototype/app/` 全部 16 个页面 ↔《系统详细设计与接口契约规范（Detailed Design & API Specification）》现行版本（575 行 / 30880 B）
> **判定时间**：2026-10-25
> **证据基础**：三份字段级盘点报告（`docs/analysis/raw/student.md` 206 条 / `raw/teacher.md` 176 条 / `raw/admin-global.md` 110 条，合计 **492 条数据需求**），逐条标注 `文件名:行号`，全部经源码复核。

## 0. 结论摘要

### 0.1 一句话结论

**不能直接对接。** 但不是"设计错了"，而是**契约只覆盖了系统的 1/5**——它把"学生做题 + AI 对话 + 查重"这一条纵向链路设计得非常完整（9 个端点、9 张表、SSE 六事件、Feign 四客户端、RabbitMQ + Go-Judge 协议），却完全没有覆盖围绕这条链路的**周边业务面**（登录、题库、作业、考试、学情、管理）。

### 0.2 三个层次的判定

| 层次 | 判定 | 说明 |
|---|---|---|
| **语法层**（字段名、枚举、单位、ID） | ❌ **不兼容** | 9 类硬冲突（枚举 4 类、ID 1 类、时间 1 类、单位 1 类、状态机 1 类、语义反向 1 类），直接传值必然错 —— 逐条见第 3 章 |
| **语义层**（业务闭环） | ❌ **不闭合** | 16 个页面里有 13 个页面的数据需求 **0 覆盖**；作业提交、考试交卷、题目 CRUD 三条主业务闭环完全断裂 |
| **架构层**（服务边界、实时通道） | ⚠️ **部分可用** | 已定的 5 个服务边界、RabbitMQ 判题链路、SSE 协议可复用；但缺管理面服务、缺考试实时通道、缺沙箱可观测 |

### 0.3 量化结论

| 指标 | 数值 |
|---|---:|
| 原型页面 | 16（门户 1 + 学生 6 + 教师 7 + 管理 2） |
| 契约现有 HTTP 端点 | **9**（8 个小节，3.3 节含 GET + PUT 两个方法） |
| 契约现有 MySQL 表 | 9 |
| 契约现有 Redis Key 类型 | 6 |
| 契约现有 OpenFeign 客户端 | 4 |
| 原型字段级数据需求 | **492 条** |
| 其中「现有端点直接覆盖」（A 类） | **40 条 = 8.1%** |
| 其中「表够、缺接口」（B 类） | **225 条 = 45.7%** |
| 其中「表缺字段」（C 类） | **90 条 = 18.3%** |
| 其中「无任何表落点」（D 类） | **76 条 = 15.4%** |
| 其中「纯前端派生」（E 类） | **61 条 = 12.4%** |
| **数据需求零覆盖的页面** | **13 / 16**（仅 `s-workbench`、`s-exam`、`t-plagiarism` 有 A 类） |
| 前端真实网络调用数 | **0**（全站 grep `fetch(` / `XMLHttpRequest` / `EventSource` / `WebSocket`，零命中） |

**这组数字的含义**：A 类 8.1% 说明"今天就能跑"的部分只有一小块；B 类 45.7% 是"表基本够、缺查询接口"——工作量主体但技术风险最低；**C + D 合计 33.7% 说明三分之一的页面需求根本无处落库**，这才是真正需要动数据模型的部分。

### 0.4 解决方案结论

采用 **「契约增量扩写到 v2.0 + 前端插入 API 适配层」** 的双轨方案（详见第 7 章）：

- **契约侧**：在 v1.0 的 9 个端点上**严格增量**扩到 **87 个端点**（新增 78），新增 **8 张表 + 26 个列**、Redis Key 6→12 类、Feign 方法 8→19、SSE 通道 1→3，**不修改任何既有端点路径与既有枚举语义**（数量与清单以 `02-契约补全规范-v2.0.md` §1.4 / §8.1 / 第 12 章为准）。
- **前端侧**：**不动 DOM 结构与 class 名**（第五轮视觉整改已验收），在 Alpine 组件与常量之间插入一层 `api/` 适配层 + `adapter/` 字段转换层，并保留 `?mock=1` 开关使答辩断网可演示。
- **不采用**：改前端去迁就契约（会推翻已验收的 5 档难度规范与 16 页视觉成果）、推翻契约重写（会破坏 PRD 验收条款锚定与论文正文）。

## 1. 判定方法

### 1.1 为什么不能只看"字段名对不对"

常见的对接评估只做字段名比对，会得出"改改命名就行"的错误结论。本报告采用**五级判定**，把"能不能对接"拆成可计量的问题：

| 判定 | 含义 | 修复动作 | 本次条数 |
|---|---|---|---:|
| **A** | 现有端点响应里有同名/同义字段 | 前端直接对接 | 40 |
| **B** | 9 张表里有字段，但没有查询端点 | 新增端点（写 SELECT） | 225 |
| **C** | 表存在，但缺列 / 缺精度 / 缺单位 | `ALTER TABLE` | 90 |
| **D** | 连表都没有 | 新增表 | 76 |
| **E** | 可由已有数据算出 | 前端计算 | 61 |

**关键判据**：只有 A 类是"现在就能跑"。B/C/D 三类都必须改动后端。**因此"能否对接"的判定标准就是 A 类占比是否足够高**——8.1% 显然不够。

### 1.2 判定口径的两个刻意选择

**（1）A 类从严。** 字段名不同但语义相同也算 A（例如契约的 `statusLabel` 覆盖原型 `OJ.statusName(s)` 的输出）。反过来说，**语义不同一律降级**——例如原型 `left: '2 天'`（预格式化中文）与契约 `end_time DATETIME` 看着都能表达"剩余时间"，但前者无法排序、无法国际化、跨月即错，因此判为 C 而非 A。

**（2）E 类不免费。** 61 条 E 类里有 7 条（`M05/M17/M18/M19/A03/A18/A46`）**依赖 C/D 类字段先存在**——字段不补，前端无数据可算。这类"伪 E 类"在实施时必须和它的依赖项一起排期。

### 1.3 证据强度说明

所有 492 条需求均标注了 `文件名:行号`，并经过两轮复核：

- 第一轮由 3 个子代理按页面逐行审计，产出 `raw/{student,teacher,admin-global}.md`；
- 第二轮对**关键论断**做独立复核，包括：`index.html:198` 的"不需要登录"原文、`s-workbench.html` 不加载 `shell.js`（`<script` 只有 2 个且无 shell.js，全文 `OJ.` 命中 0 次）、`shell.js:470` 的 5 档难度常量、全站 `visibilitychange`/`blur` 监听零命中、`data-page` 实际取值清单（15 个业务页只有 13 个不同取值）。

### 2.3 端点能力的绝对数量差

- **学生端**：7 个 REST 里学生真正只用到 6 个（查重三个属教师端）。但学生端 6 个页面按页面归并去重后需要 **28 项接口能力**。→ 覆盖 6/28 ≈ **21%**。

- **管理端**：需要 **14 类能力**（通道 7 类 + 审计/沙箱 7 类）。→ 覆盖 **0/14 = 0%**。

三端合并去重后（判题三接口、AI 两接口、查重三接口、切屏一接口在三端复用），**v2.0 需要 87 个端点**（v1.0 保留 9 + 新增 78，清单见 `02-契约补全规范-v2.0.md` §1.4 与第 12 章），相对 v1.0 的 9 个是 **9 倍扩张**。这里刻意**按资源而不是按页面**切端点：同一个资源被多页消费时只出一个端点、用参数区分视角（`02` §1.4 三处合并），所以「28 项学生端能力 + 38 项教师端能力 + 14 类管理端能力 = 80 项能力」被压到 78 个新端点上（`02` §1.4 的「三处合并」：状态流转合一、统计内嵌、胶囊内嵌），压缩比约 1.03 : 1。

## 3. 证据二：九类硬冲突（逐条带证据）

> 这一章回答"就算把接口补齐，前端能不能直接对接"。答案是**不能**——即使端点全部就绪，以下 9 类冲突会让数据在传输层就失真。

### 3.1 判题状态：int 0–9 vs 小写字符串

| 侧 | 形态 | 证据 |
|---|---|---|
| 契约 | `status TINYINT`，0 排队 / 1 编译 / 2 评测 / 3 AC / 4 PAC / 5 WA / 6 TLE / 7 MLE / 8 RE / 9 CE | 契约 `judge_submission` DDL |
| 原型 | 小写字符串 `'ac'/'wa'/'tle'/'mle'/'re'/'ce'/'pac'/'pending'/'none'` | `shell.js:463-466` `statusName()` |

**冲突性质**：不是"改名"，是**类型不同**。前端 `OJ.statusTag(s)` 直接把入参当 CSS class 用（`shell.js:468`：`'<span class="tag ' + s + ...`），所以 `s` 必须是 `'ac'` 这样的小写词。若后端直接返回 `3`，样式表 `.tag.ac` 永远不命中，全站判题标签会**无样式裸奔**。

**还有两个值根本不属于判题状态**：`none`（未提交，是列表行的"我还没做"状态）与 `run/idle`（沙箱实例状态，`shell.js:436`）。契约的 0–9 里没有它们的位置。

**解法**：契约 1.3 与新增的提交查询接口**同时返回三个字段**——`status`（int 真值）、`statusCode`（小写，供 CSS）、`statusLabel`（大写，供展示）。加两个派生字段（不新增列），前端零改动。

### 3.2 难度：3 档 vs 5 档

| 侧 | 形态 | 证据 |
|---|---|---|
| 契约 | `difficulty TINYINT`，1 简单 / 2 中等 / 3 困难 | 契约 `prob_question` DDL |
| 原型 | 5 档 `1 入门 / 2 简单 / 3 中等 / 4 较难 / 5 困难` | `shell.js:470` `lvlName()`；`_SPEC.md:105` 明文规定 |

**这是最难"改前端"的一处**，因为 5 档已经写进了**规范级文件** `_SPEC.md:105`（"`OJ.lvlName(n)` // 1→'入门' 2→'简单' 3→'中等' 4→'较难' 5→'困难'"），且被 6 处引用：题库筛选（`?lvl=4/5` 深链）、题库列表 `lvl()` 的 5 格刻度条、工作台徽标（`title="难度 3 / 5"`）、作业抽屉、学情表、考试题号列表。

**关键判断**：如果改成 3 档，`?lvl=4` 与 `?lvl=5` 两条深链永远筛不出题；`OJ.lvl()` 的 5 格刻度条要么改 DOM（违反"不动视觉"红线），要么永远只亮 3 格。**因此扩契约、不改前端**。

**解法**：`difficulty` 取值域扩为 1–5，语义重新映射（旧 1→新 2，旧 2→新 3，旧 3→新 5），新 1（入门）与新 4（较难）为新增档。迁移 SQL 见基线文档 §5.2。

### 3.3 语言：`cpp/java/python` vs `C++ 17/Python 3/Java 17`，且原型自身不统一

| 侧 | 形态 | 证据 |
|---|---|---|
| 契约 | `language VARCHAR(16)`，注释 `'cpp/java/python'` | 契约 `judge_submission` DDL |
| 原型 A 处 | `'C++ 17'`（**带空格**） | `s-submissions.html:710` `langs: ['all','C++ 17','Python 3','Java 17']`；`:793` palette 三个键 |
| 原型 B 处 | `'C++17'`（**不带空格**） | `t-plagiarism.html:474-490` |
| 原型 A 处再一处 | 三个 `<option>` 同款带空格写法 | `a-audit.html:459-461` |

**这条冲突暴露了原型自身的问题**：连"显示名"都没统一。若直接对接，`t-plagiarism` 的语言筛选会对不上任何数据。

**解法**：传输层一律 `cpp/java/python`；展示名由 `languageLabel` 字段下发（`C++ 17` / `Java 17` / `Python 3`），或前端用一张字典渲染。**禁止在业务代码里散写字面量**。

### 3.4 ID 命名空间：`S-20481` / `P-1024` vs `BIGINT`

| 实体 | 契约 | 原型 | 证据 |
|---|---|---|---|
| 提交 | `judge_submission.id BIGINT AUTO_INCREMENT` | `'S-20481'` | `shell.js:348` |
| 题目 | `prob_question.id BIGINT AUTO_INCREMENT=1001` | `'P-' + pid` | `t-problem-edit.html:292` |
| 作业 | `teach_assignment.id BIGINT` | `'A-0412'` | `shell.js` `ASSIGNMENTS` |
| 查重 | `teach_plagiarism_report.id BIGINT` | `'P-0088'` | `shell.js` `PLAGIARISM` |
| 沙箱 | **无表** | `'sbx-8841'` | `a-audit.html` `BOX_STATE` |

**`P-` 前缀撞车**：原型里 `P-1024` 是题目、`P-0088` 是查重报告——**同一个前缀表达两个实体**。这是原型自身的一个语义缺陷，对接时必须分开。

**解法**：主键全部保持 `BIGINT`（进索引、进外键），另加 `display_no VARCHAR(16)` 唯一列（`S-20481` / `A-0412` / `P-0088` / `sbx-8841`），由服务端用 Redis `INCR` 生成。**前端不得自行拼前缀**——并发下会撞号。

### 3.5 时间：`DATETIME` / 预格式化中文 vs epoch

| 侧 | 形态 | 证据 |
|---|---|---|
| 契约 | `create_time DATETIME`、`start_time` / `end_time` | `judge_submission` / `teach_assignment` DDL |
| 原型 | `at: '10-24 23:41'`（无年份无时区）、`left: '2 天'` / `'已结束'`（预格式化中文） | `shell.js` `SUBMISSIONS` / `ASSIGNMENTS` |
| `_SPEC.md` | **全文 0 处规定时间格式** | 逐行核对 |

**`left` 是真实 bug，不只是格式问题**：`s-assignments.html:651` 与 `:670` 的排序靠 `parseInt(a.left)`，而 `parseInt('已结束')` 是 `NaN`，`parseInt('2 天')` 是 `2`——跨月后"12 天"会排到"2 天"前面。

**另一处衍生缺陷**：`a-audit.html:877` 用 `localeCompare` 比较 `at` 字符串，跨日排序错；`a-models.html:512` 把 `at` 当 `x-for` 的 key，同分钟多条会撞 key。

**解法**：接口层一律传 **epoch 毫秒**（字段名以 `At` 结尾：`dueAt` / `submittedAt`），相对时间（"2 天"）由前端计算。这一条同时修掉原型里 3 个真实缺陷。

### 3.6 单位：三处 1024 倍 / 1000 倍误差隐患

| 域 | 契约 | 原型 | 误差 |
|---|---|---|---|
| 通道超时 | `timeout_seconds INT DEFAULT 8`（**秒**） | `CFG.timeout = 8000`（**毫秒**），展示 `${timeout}ms` | **1000×**（8 秒会渲染成 8000 秒） |
| 沙箱内存 | Go-Judge `memoryLimit: 268435456`（**字节**） | `OJ.sandbox.mem = 51200` → 展示 `50.0 MB`（**KB**） | **1024×** |
| 判题内存 | `memory_used INT`（注释：最大 KB） | 判题展示 `'4210KB'` | 一致，但库表 `memory_limit INT DEFAULT 256` 是 **MB**，同名字段两种单位 |

**最危险的是第三条**：`prob_question.memory_limit`（MB）与 `judge_submission.memory_used`（KB）**字段名相似但单位差 1024 倍**，任何人凭直觉做减法都会错。

**解法**：所有新增字段强制带单位后缀（`timeoutMs` / `memoryKb` / `timeUsedMs` / `costCents`）；`ai_model_config.timeout_seconds` 改名 `timeout_ms`；字节↔KB 换算**只允许发生在 `oj-judge-service` 调 Go-Judge 的适配层**，且必须有单测。

### 3.7 沙箱状态：`run/idle` vs `running/queued/exited`

| 侧 | 取值 | 证据 |
|---|---|---|
| `shell.js` | `run` / `idle` 两态 | `shell.js:436` `SANDBOX` |
| `a-audit.html` | `running` / `queued` / `exited` 三态 | `a-audit.html:716` `BOX_STATE` |

**原型内部就不一致**——`shell.js` 的共享常量与页面自己的常量用了两套状态词。而契约里**根本没有沙箱实例概念**（Go-Judge 是同步 `/run`，没有容器实体）。

**解法**：新建 `judge_sandbox_instance` 表，状态机 `QUEUED → RUNNING → EXITED/KILLED`（四态），废弃 `shell.js` 的 `run/idle` 两态常量。

### 3.8 难度之外的两处语义反向：`weak_tags` 与 `guardrail_action`

**（1）`sys_user.weak_tags` 语义与学情页相反。**
`weak_tags` 是"错题标签 → 次数"（**越高越弱**）；而 `s-analytics.html` 的 `TAGS` 与 `t-analytics.html` 的 `KP_BASE` 是"AC 占比"（**越高越强**）。且 `weak_tags` 缺分母、缺班级维度、缺时间区间，而两页都有"本周/本月/学期"切换。

**更关键的是**：两页的 `pct` **完全同源同值**——`s-analytics` 的 `TAGS` 硬编码 `82/64/41/73/55`，`t-analytics` 的 `KP_BASE` 也是 `{动态规划:82, 贪心:64, 图论:41, 字符串:73, 数学:55}`，再叠加伪随机抖动。也就是说**学生看到的"我的掌握度"和教师看到的"班级掌握度"是同一组写死常量**，只是套了不同的壳。

**解法**：`weak_tags` 降级为快照缓存；真实统计走 `judge_submission` + `teach_student_score` 按 `(class_id, tag, time_range)` 聚合，新增 `GET /api/teaching/analytics/class/{classId}/knowledge` 与 `GET /api/teaching/analytics/student/{sid}`。

**（2）`guardrail_action` 单值无法还原原型的三分类。**
契约 `0` 通过 / `1` 输入侧防注入阻断 / `2` 输出侧超 5 行熔断；原型 `pass` 通过 / `rewrite` 输出改写 / `block` 输出侧整段题解丢弃。

若按 `0→pass / 2→rewrite / 1→block` 映射，"越狱尝试被输入过滤拦下"与"整段题解被输出拦截"会被合并成同一个 `block` 计数——而 `a-audit.html` 的 `hitDist` 恰恰要区分"泄漏率 4 / 越狱特征 2 / 敏感词 1"三个数，**永远分不开**。

**解法**：拆成两维——`guardAction`（0/1/2，动作）+ `guardReason`（`LEAK_RATE` / `JAILBREAK` / `SENSITIVE_WORD` / `OVER_LENGTH_CODE` / `NONE`，原因）。这是**把一维动作扩成两维**，不改既有枚举语义。

### 3.9 实时通道：全站只有 1 个 SSE，且前端零调用方

| 能力 | 契约 | 前端 |
|---|---|---|
| AI 对话流式 | ✅ `POST /api/ai/chat/stream`（6 种事件） | ❌ 零调用（`REPLIES` 硬编码，`s-workbench.js:222-241`） |
| 判题进度 | ❌ 只有轮询 `GET /api/judge/status/{id}` | ❌ `setTimeout` 92ms/96ms 点格（`s-workbench.js:120-156`） |
| 考试监考 | ❌ 无 | ❌ 静态数组 |
| 查询任务进度 | ❌ 无 | ❌ 只 toast「预计 40 秒后完成」 |
| 沙箱状态 | ❌ 无 | ❌ `autoRefresh` 开关不绑定任何定时器 |

**最讽刺的一条**：契约里唯一为"考试防作弊"设计的接口 `POST /api/teaching/exam/tab-switch`，**在前端根本没有调用方**——全站对 `prototype/app/*.html` + `*.js` 全量 grep `visibilitychange` / `blur` / `onblur`，**零命中**。`s-exam.html:235` 只有一句文案"切屏超过 3 次记为异常"，`:368` 是写死的"切屏次数 0"。

→ **两端都缺，且缺的是同一条链路的两半。**

## 5. 三个"最小复现"：为什么改改字段名解决不了

用三个可以直接在浏览器里复现的场景，说明问题的性质。

### 复现 A：打开 `s-workbench.html`，点"提交评测"

**现状**：`submit()`（`s-workbench.js:120-156`）里的 `willPass = this.fixed` 决定结果，`setTimeout` 每 92/96ms 点亮一格，10 格全亮后 300ms 翻成 `ac` 或 `wa`。

**如果只补接口不改逻辑**：接上 `POST /api/judge/submit` 拿到 `submissionId`，然后轮询 `GET /api/judge/status/{id}`——**这一步是可以走通的**（契约 1.3 有 `caseDetails[{caseId,status,timeMs,memKb}]`）。但接下来：

- 页面要显示"第 3 个测试点：全负数组 → 期望 `-1`，实际 `-3`"，而 `caseDetails` 里**只有 `caseId/status/timeMs/memKb`，没有输入、没有期望输出、没有实际输出**；
- 页面要显示"测试点 3 对应你代码第 8 行"，而这个映射在真实判题系统里**不存在**（`s-workbench.js:14` 的 `CASE_LINE` 源码注释自认是"叙事道具"）；
- 页面要点亮"10 格"并显示语义名（`CASE_LABELS`：sample/全负/边界/全正/混合/大数据/随机/极限），而契约里 `caseId` 只是序号。

→ **补接口只能点亮格子，画不出叙事。** 这就是为什么 `s-workbench` 的 47 条需求里仍有 8 条 C 类 + 6 条 D 类。

### 复现 B：打开 `s-assignments.html`，点"交作业"

**现状**：`handIn()` 只把本地布尔值置 `true` + `OJ.toast('已提交')`，刷新即回到未交状态。

**如果只补接口**：契约里**没有任何"交作业"端点**，也没有 `assignment_submission` 表。作业完成度只能靠 `teach_student_score`（单题最高分）反推——但那样算不出"这份作业是否正式提交"、"是否逾期提交"、"提交后还能不能改"。

→ **这是缺表，不是缺接口。**

### 复现 C：打开 `s-exam.html`，等倒计时

**现状**：`secs` 初值写死 `38*60+24`（604 秒），刷新即重置。

**如果只补接口**：需要 `GET /api/teaching/exam/{examId}/remaining`（`02` §6.4）返回服务端权威剩余时间。但 v1.0 契约里也没有——而且**即使补了这个接口，切屏检测依然不工作**，因为前端根本没有 `visibilitychange` 监听。

→ **这是两端都缺。**

## 6. 结论分级：把 492 条需求分成四类工程动作

| 类别 | 条数 | 占比 | 工程动作 | 典型代表 |
|---|---:|---:|---|---|
| **可直接对接** | 40 | 8.1% | 前端把常量换成响应字段 | `s-workbench` 的判题三接口、`t-plagiarism` 的查重三接口 |
| **补查询接口即可** | 225 | 45.7% | 写 SELECT + 加端点（不动表） | 题目/作业/提交/学情四类列表，共 91 条学生端 B 类 |
| **必须改数据模型** | 166 | 33.7% | C 类 `ALTER TABLE` 90 条 + D 类建表 76 条 | 沙箱实例、测试点实体、查重分段、作业提交、可观测性字段 |
| **前端自算** | 61 | 12.4% | 无需后端（其中 7 条依赖 C/D 先落地） | 合计、占比、倒计时、排序 |

**排期建议**：B 类 225 条是工作量主体但**技术风险最低**（纯 CRUD），应作为第一批；C/D 类 166 条决定系统能不能讲圆，应在 B 类之后集中处理；A 类 40 条可作为"早期打通链路"的验证样本，第一天就可以做。

## 7. 解决方案

### 7.1 三条路线对比

| 方案 | 做法 | 优点 | 致命缺点 | 结论 |
|---|---|---|---|---|
| **A. 改原型适配契约** | 把 5 档难度降到 3 档、把小写状态改成 int、删掉 10 格判分链、砍掉查重分段与沙箱监控 | 后端零改动 | 推翻第五轮已验收的视觉成果（commit `8ec9fda`）；`_SPEC.md:105` 的规范级约定被破坏；查重页与沙箱页直接失去核心体验；**等于把 16 个页面砍成 8 个** | ❌ 否决 |
| **B. 契约增量扩写 + 前端插入适配层** | 契约从 9 个端点扩到 87 个（严格增量、不改既有）；前端加 `api/` + `adapter/` 两层，DOM 一行不动 | 保留全部视觉成果；破坏性变更 0；可按 P0/P1/P2 分批交付 | 后端工作量大（新增 8 表 26 列 + 78 端点） | ✅ **采用** |
| **C. 推翻重写** | 重写契约 + 重写前端（迁 Vue） | 架构最干净 | 时间成本不可接受；会毁掉已写好的论文段落与答辩 PPT 素材 | ❌ 否决 |

### 7.2 选定方案 B 的三条理由

**（1）契约的"纵向链路"设计是对的，不该推倒。**
判题链路的 RabbitMQ 削峰 → Go-Judge 沙箱 → `first_failed_summary` 精确定位首个失败点，SSE 的六事件设计（`router_step` 路由决策 / `tool_calling` 工具调用 / `fallback_notice` 降级提示 / `guardrail_rewrite` 护栏改写），这些是有深度的设计，推倒重来只会更差。**它缺的是横向铺开，不是纵向深度。**

**（2）原型的视觉规范是资产，不是负债。**
`_SPEC.md` 里的 6 级字号、颜色只取 token、强调色 ≤10%、四态（loading/empty/error/normal）、空态必写——这是一套完整的、经五轮整改的设计系统。为了迁就一个 `difficulty` 字段的取值域去改它，性价比极低。

**（3）"不动 DOM 只换数据源"在 Alpine.js 下是可行的。**
Alpine 的 `x-data` 组件本质上就是"状态对象 + 模板绑定"。把 `OJ.problems` 常量换成 `this.list`（初值 `[]`，`init()` 里 `await` 填充），模板一行不用改。这是本次改造能在 2~3 周内完成的技术前提。

### 7.3 方案 B 的具体形态

```
┌─────────────────────────────────────────────────────┐
│  prototype/app/*.html（DOM 与 class 一行不动）        │
│    x-data="problemsPage()"                           │
└──────────────────┬──────────────────────────────────┘
                   │ this.list / this.total / this.loading
┌──────────────────▼──────────────────────────────────┐
│  页面组件（Alpine 对象）                              │
│    删除：OJ.problems 常量引用、setTimeout 模拟        │
│    新增：async init()、轮询句柄、SSE 句柄             │
└──────────────────┬──────────────────────────────────┘
                   │
┌──────────────────▼──────────────────────────────────┐
│  adapter/  字段适配层（本项目新增，7 张映射表）        │
│    status: 3 → 'ac'（int 0–9 → 小写 class）    difficulty: 3 → '中等'（5 档同名）    │
│    at: 1761310860000 → '10-24 23:41'                 │
│    memoryKb: 4210 → '4210KB'                         │
└──────────────────┬──────────────────────────────────┘
                   │
┌──────────────────▼──────────────────────────────────┐
│  api/  请求层（本项目新增）                           │
│    http.js  token / traceId / 错误码 / 401 跳登录     │
│    sse.js   fetch + ReadableStream（带 Authorization）│
│    MOCK 开关：?mock=1 时走 mock/index.js（搬 shell.js）│
└──────────────────┬──────────────────────────────────┘
                   │
        http://localhost:8080/api/...
```

**关键设计：`?mock=1` 开关。**
把现有 `shell.js` 的全部常量搬进 `mock/index.js`，`http.js` 里判断 `location.search.includes('mock=1')` 或 `localStorage.OJ_USE_MOCK`：

- `mock=1` → 返回 `Promise.resolve(旧常量)`，**答辩现场断网也能演示，且演示的是同一套 UI**；
- 无 `mock` → 走真实 `fetch`。

这一条对毕设答辩有决定性意义：**改造过程中任何时刻页面都能跑**，不会出现"改到一半演示不了"的尴尬期。

## 10. 给答辩的三句话

如果被问到"原型和接口契约能不能对接"，可以这样答：

> **第一句（结论）**：不能直接对接，但差距是可量化的，不是设计错误。492 条页面需求里，现有 9 个端点直接覆盖 40 条（8.1%），45.7% 是"表够缺接口"，33.7% 需要改数据模型。
>
> **第二句（原因）**：契约在"学生做题 + AI 对话 + 查重"这条纵向链路上设计得很完整——RabbitMQ 削峰、Go-Judge 首个失败点摘要、SSE 六事件、四阶段 AI 管控，这些是有深度的；但它没有横向铺开，16 个页面里有 13 个的首页数据都拿不到，管理端更是 0 覆盖。
>
> **第三句（方案）**：所以我做的是**契约增量扩写 + 前端插入适配层**：契约从 9 个端点严格增量扩到 87 个（不改任何既有端点与枚举语义），前端不动 DOM 与 class，只把"常量"换成"异步状态"，并保留 `?mock=1` 开关使改造全程可演示。视觉成果零损失，破坏性变更零。
