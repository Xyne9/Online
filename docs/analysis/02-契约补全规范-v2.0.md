1. v1.0 的 9 个端点：路径、方法、请求字段名、响应字段名、判题状态 `0–9` 数值语义**逐字不变**；只允许新增字段（如 `status` 旁新增 `statusCode`），老前端忽略新字段即可继续工作。
2. 6 类 Redis Key 的格式与 TTL 不变；新增 Key 一律新前缀，不复用旧 Key 的类型。
3. RabbitMQ 交换机/队列/路由键三件套不变；`JudgeTaskMessage` 只允许追加字段。
4. Go-Judge `POST http://localhost:5050/run` 的 `cmd[] / cpuLimit / clockLimit / memoryLimit / procLimit / copyIn` 语义不变；`instanceTag` 为**可选**，旧镜像不认则忽略。
5. 响应包装 `{code,message,data,traceId}` 不变：`code` 与 HTTP 状态码同值；出错 `data` 为 `null`；`null` 字段保留不裁剪。
6. 分页 `data:{list,total,page,pageSize,hasNext}` 不变；`pageSize` 超过 100 按 100 处理，不报错。

九码定义（基线 §3.4，全文只引用这 9 个）：

| code | 语义 | 典型触发 |
|---:|---|---|
| 200 | 成功 | — |
| 400 | 参数校验失败 | 缺必填、枚举越界、`sortBy` 不在白名单、测试点合计 ≠ 100 |

| 409 | 状态冲突 | 重复提交、已结束考试交卷、已归档题目编辑 |
| 429 | 限流防抖 | 3 秒内重复提交、AI 配额耗尽、SSE 并发超限 |

## 2. `/api/auth` 认证与用户（5 个端点，`oj-teaching-service`）
### 2.1 鉴权链路
```
浏览器 ──login──▶ oj-teaching-service ──BCrypt.matches──▶ sys_user
                        ├─ 签 JWT（HS256，载荷见 §2.7）
                        ├─ SET oj:auth:token:{userId}   = JWT          EX 24h
                        └─ SET oj:auth:refresh:{userId} = refreshToken EX 7d
浏览器 ──Authorization: Bearer <JWT>──▶ 网关 ──▶ 各服务 AuthFilter
                                              ├─ 校验签名 / exp / jti
                                              └─ GET oj:auth:token:{userId} 逐字比对
```

JWT **不是无状态的**：每次请求回查 `oj:auth:token:{userId}`，值不等即视为已注销（401）。这样 `logout` 才有意义，也避免「改密码后旧 token 仍可用」。
### 2.2 `POST /api/auth/login` 登录
**用途**：账号密码登录，签发 access/refresh token，返回用户卡与落地路由。
**原型**：`index.html:189-222`（登录表单）、`shell.js:90-94`（`OJ.ROLES` 三角色档案）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| username | string | 是 | 学号/工号，2–32 字符 |
| password | string | 是 | 明文密码，6–64 字符，服务端 BCrypt 校验 |
| rememberMe | boolean | 否 | true 时 refresh 7 天，否则 12 小时 |

**成功响应**

```json
{"code":200,"message":"ok","data":{"accessToken":"eyJhbGciOi...","refreshToken":"rt_9f2c...","expiresIn":86400,"user":{"id":1024,"username":"20220101","realName":"林昭","role":"STUDENT","roleLabel":"学生","classId":1,"className":"计算机2022级1班","avatarText":"林"},"homePath":"s-problems.html"},"traceId":"7f3c..."}
```

**错误码**：400（账号或密码为空）｜401（账号或密码错误，统一文案，不区分账号是否存在）｜403（`sys_user.status = 0`）｜429（同 IP 每分钟 10 次）
**备注**：`homePath` 按角色下发 `s-problems.html` / `t-dashboard.html` / `a-models.html`，落地判断不在前端硬编码。
### 2.3 `POST /api/auth/logout` 注销
**用途**：删除服务端 token，access 与 refresh 同时失效。
**原型**：`shell.js:161-165`（用户卡下拉「退出登录」，原型为死按钮）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| allDevices | boolean | 否 | true 清空该用户全部会话，默认 false |

**成功响应**：`{"code":200,"message":"ok","data":{"loggedOut":true},"traceId":"7f3c..."}`
**错误码**：401（token 已失效）
**备注**：幂等——token 已不存在也返回 200；`allDevices=true` 额外删 `oj:auth:refresh:{userId}`。
### 2.4 `POST /api/auth/refresh` 续期
**用途**：用 refresh token 换新 access token，避免 24 小时到点被踢。
**原型**：`shell.js:161-165`（前端静默续期，无独立页面）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| refreshToken | string | 是 | 登录时下发的刷新令牌 |

**成功响应**：`{"code":200,"message":"ok","data":{"accessToken":"eyJhbGciOi...","refreshToken":"rt_3a71...","expiresIn":86400},"traceId":"7f3c..."}`
**错误码**：401（refresh 过期或与 `oj:auth:refresh:{userId}` 不匹配）｜403（用户已禁用）
**备注**：轮换策略——每次刷新同时签发新 refresh 并覆盖 Redis，旧 refresh 立即失效（防重放）。

### 2.7 JWT 载荷 schema
| 字段 | 类型 | 说明 |
|---|---|---|
| sub | string | 用户名（`sys_user.username`） |
| uid | long | 用户 ID，服务层越权校验用 |
| role | string | `STUDENT` / `TEACHER` / `ADMIN`（基线 §5.6） |
| cid | long\|null | 班级 ID；教师为所带班，管理员为 null |
| jti | string | 令牌唯一 ID（UUID），与 Redis value 内 jti 比对 |
| iat / exp | long | 签发/过期秒级时间戳，`exp - iat = 86400` |

Header 固定 `{"alg":"HS256","typ":"JWT"}`；密钥 `oj.auth.jwt-secret` 从环境变量注入（≥32 字节，不进 Git）。
### 2.8 401 / 403 语义分界
| 场景 | HTTP | 前端动作 |
|---|---|---|
| 无 `Authorization` 头 | 401 | 跳登录页，带 `?redirect=` |
| 签名错 / 过期 / 与 Redis 不匹配 | 401 | 清本地 token，跳登录页 |
| 角色不匹配（学生访问 `/api/admin/**`） | 403 | 停在当前页，`OJ.toast('无权限')` |
| 访问他人资源（`submissionId` 非本人） | 403 | 同上，服务层 `WHERE user_id = currentUserId` |
| 教师访问非自己所带班级 | 403 | 同上，校验 `teach_class.teacher_id` |

原则：**认证失败 401，授权失败 403**；两者都不返回具体原因（不泄露资源是否存在的探测通道），细节只写进 `traceId` 对应日志。
## 3. `/api/problem` 题库（13 个端点，`oj-problem-service`）
### 3.1 域说明
| 约束 | 内容 | 依据 |
|---|---|---|
| 难度 | `difficulty` 1–5，标签取 `OJ.lvlName`：入门/简单/中等/较难/困难 | 基线 §5.2，`shell.js:470` |
| 展示号 | `id` BIGINT ≥ 1001，前端渲染 `#1024` | 基线 §6，`t-problem-edit.html:292` |
| 状态 | `state` 0 草稿 / 1 已发布 / 2 已归档 | 基线 §5.6、§8 |

```
0 草稿 ──publish(测试点合计=100)──▶ 1 已发布 ──archive──▶ 2 已归档
                                        ▲                    │
                                        └────── restore ◀─────┘
```

### 3.15 `prob_test_case` 新表 DDL（评审必看②）
`t-problem-edit.html` 的测试点表需要**四个维度**同时落地：类型四档、分值、开放标志、顺序。v1.0 只有 `prob_question.test_case_dir`（目录名）和 `test_case_count`（数量），四个维度一个都撑不住——这也是 `s-problems.html:473-481` 里前端只能用 `Math.round(score/100*10)` 反推判分链的根因（注释自认「题库没有逐测试点数据」）。

```sql
CREATE TABLE `prob_test_case` (
  `id`            BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
  `problem_id`    BIGINT       NOT NULL COMMENT '所属题目 prob_question.id',
  `seq_no`        INT          NOT NULL COMMENT '测试点序号，从 1 起，同题内连续；判分链格子顺序即此序',
  `kind`          VARCHAR(16)  NOT NULL DEFAULT 'normal' COMMENT '类型四档：sample 样例 / normal 普通 / edge 边界 / stress 构造',
  `input_text`    MEDIUMTEXT   NOT NULL COMMENT '标准输入全文',
  `output_text`   MEDIUMTEXT   NOT NULL COMMENT '期望输出全文',
  `score`         INT          NOT NULL DEFAULT 0 COMMENT '该点分值 0-100，同题合计须=100 才可发布',
  `is_public`     TINYINT(1)   NOT NULL DEFAULT 0 COMMENT '是否对学生开放：1 公开（样例，可见输入输出）/ 0 隐藏',
  `input_size`    INT          NOT NULL DEFAULT 0 COMMENT '输入字节数，列表页展示用，写入时算好',
  `output_size`   INT          NOT NULL DEFAULT 0 COMMENT '输出字节数',
  `deleted_at`    DATETIME     NULL     DEFAULT NULL COMMENT '软删时间，NULL 为有效',
  `create_time`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_prob_seq` (`problem_id`, `seq_no`, `deleted_at`) COMMENT '同题内序号唯一，软删后序号可复用',
  KEY `idx_prob_kind` (`problem_id`, `kind`) COMMENT '按类型聚合 kindSummary',
  KEY `idx_prob_public` (`problem_id`, `is_public`) COMMENT '学生端只取公开点'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci COMMENT='题目测试点，替代 v1.0 的 test_case_dir 目录约定';
```

**四件事如何被支撑**

| 原型需求 | 原型位置 | 表字段 | 说明 |
|---|---|---|---|
| 类型四档 `sample/normal/edge/stress` | `t-problem-edit.html:432-441` 的 `<select x-model="tp.kind">` | `kind` | 四值严格对齐；`t-problems.html` 的 `hidden` 是**旧两档模型**，读接口时映射 `hidden→normal`（见 §3.9 备注） |
| 分值 0–100 | `:449-451` `tp.score`（min=0 max=100 step=5） | `score` | 服务端也校验 5 的倍数；`totalScore` 为 `SUM(score)` |
| 开放标志 | `tp.open` | `is_public` | **`tp.open` 只是 UI 展开态，不落库**；落库的是 `is_public`（是否对学生开放），两者名字接近但语义不同，前端不要把 `tp.open` 直接提交上来 |
| 顺序 | `x-for="(tp,i) in tps"` 的下标 | `seq_no` | 前端拖拽/增删后重排数组，批量保存时按下标重写 `seqNo` |

**与 v1.0 `test_case_dir` 的关系**：`prob_test_case` 是**权威数据源**；`test_case_dir`/`test_case_count` 保留为「物化产物」——保存测试点时异步把 `.in/.out` 文件写到该目录（供 Go-Judge `copyIn` 用），`test_case_count` 同步为有效行数。两处不一致时以表为准，由 §7 的运维任务重刷。

**旧数据迁移**：`INSERT INTO prob_test_case (problem_id,seq_no,kind,score,is_public) SELECT id, n, IF(n<=2,'sample','normal'), IF(n<=2,10,80/(test_case_count-2)), IF(n<=2,1,0) FROM prob_question JOIN (SELECT 1 n UNION SELECT 2 ...) WHERE ...`——按现有 `test_case_count` 生成占位行，`.in/.out` 内容由目录回填脚本补齐（一次性任务，失败则题目保持草稿）。

2. **内存单位换算唯一入口**：`prob_question.memory_limit`（MB）×1024×1024 → Go-Judge `memoryLimit`（字节）；Go-Judge 回的字节 ÷1024 → `judge_submission.memory_used`（KB）→ 下发 `memoryUsedKb`；沙箱侧 `mem_limit_kb` 同理（KB）。**只有 `JudgeAdapter` 一个类做换算，且必须有单测**（51200 KB ↔ 268435456 字节这对值直接做用例，覆盖 MB→字节、字节→KB 两个方向与四舍五入）。

**5 秒撤销的实现约定**

1. `submit` 落库即写 `assignment_submission.status='SUBMITTED'`，同时 `undo_deadline_at = now + 5000`；不搞「延迟 5 秒才落库」——那会让刷新页面丢提交。
2. `DELETE` 校验 `now < undo_deadline_at`，超时返回 **409**；前端 `OJ.toast(msg,{undo:true})` 的 5 秒倒计时（`shell.js:481-507`）与后端窗口同源，但**以服务端为准**。
3. 撤销后 `teach_student_score` 不回滚已产生的判题成绩（那是「做题成绩」，独立于「交作业」动作），只把 `assignment_submission` 置 `UNSUBMITTED`。
4. 同一作业重复 `submit` 且已超撤销窗口 → 409（基线 §3.4「重复提交」）。

### 8.2 难度 3 档 → 5 档迁移（评审必看①）
`shell.js:470` 的 `OJ.lvlName` 是 5 值数组 `['','入门','简单','中等','较难','困难']`，`_SPEC.md:105` 把「5 档难度刻度」列为规范级硬约定，全站 6 处引用；而 v1.0 `prob_question.difficulty` 注释是「1 简单/2 中等/3 困难」。若直接改注释不迁数据，历史题的「困难」会被渲染成「中等」。

**映射规则**（基线 §5.2 指定，不是自由选择）：旧 1（简单）→ 新 2（简单）；旧 2（中等）→ 新 3（中等）；旧 3（困难）→ 新 5（困难）；新增 1（入门）与 4（较难）无历史数据。

```sql
-- 步骤 1：先放宽列定义（5 档需要 1..5，原 TINYINT 足够，只需改注释与校验）
ALTER TABLE `prob_question`
  MODIFY COLUMN `difficulty` TINYINT NOT NULL DEFAULT 2
  COMMENT '难度 1 入门 / 2 简单 / 3 中等 / 4 较难 / 5 困难（v2.0 五档，基线 §5.2）';

-- 步骤 2：三步倒序迁移，避免 1→2 之后又被 2→3 二次搬走
UPDATE `prob_question` SET `difficulty` = 5 WHERE `difficulty` = 3;
UPDATE `prob_question` SET `difficulty` = 3 WHERE `difficulty` = 2;
UPDATE `prob_question` SET `difficulty` = 2 WHERE `difficulty` = 1;

-- 步骤 3：校验（必须返回 0 行）
SELECT `difficulty`, COUNT(*) FROM `prob_question`
 WHERE `difficulty` NOT BETWEEN 1 AND 5 GROUP BY `difficulty`;
```

**为什么必须倒序**：一条 `CASE WHEN` 语句在 MySQL 里是逐行原子求值、安全；但如果拆成三条正序 `UPDATE`（1→2、2→3、3→5），第二步会把刚变成 2 的行再推到 3，全部数据最终错位。要么用单条 `CASE`，要么严格 3→5、2→3、1→2 倒序。**回滚脚本**同构：`5→3`、`3→2`、`2→1`，同样倒序。

**前端对齐**：`s-problems.html:214-231` 的难度多选是 `[1,2,3,4,5]`，`?lvl=4`/`?lvl=5` 深链已存在；迁移后 4 档「较难」首次有真实数据可筛。`t-problems.html` 的 `lvlCount(n)` 统计同理。

**Go-Judge 最小改造方案**（三步，不改协议字段语义，只加旁路）：

| 步 | 改造 | 工作量 | 兼容性 |
|---|---|---|---|
| 1 | `/run` 请求体加**可选** `instanceTag`（string，最长 32）。Go-Judge 收到后把它写进容器 label / 进程环境变量 `OJ_INSTANCE_TAG`，其余字段一字不动 | 约 30 行 Go | 旧调用不传即忽略，旧镜像行为不变 |
| 2 | 新增 `POST /instances/{tag}/kill` 与 `GET /instances?state=running` 两个**只读/运维**接口，读步骤 1 打的标签；`/run` 仍是同步语义（判题链路不受影响） | 约 120 行 Go | 不影响 `/run` |
| 3 | `oj-judge-service` 在发 `/run` 前先 `INSERT judge_sandbox_instance(state='RUNNING', instanceTag=sbx-xxxx)`，再用 `@Async` 轮询 Go-Judge `GET /instances` 更新 `cpu_percent/mem_used_kb/last_heartbeat_at`；`/run` 返回后置 `EXITED` 并写 `exit_code` | 约 200 行 Java | 管理端读表，判题链路零改动 |

**为什么这算「最小」**：评审可能会问「为什么不直接上 K8s/容器编排」。因为 v1.0 的红线明确 Go-Judge 协议字段不可改（基线 §9），而全站只有一台判题机；用 label + 两个旁路接口就能让 `a-audit` 的列表/日志/终止三个动作全部有真实数据源，且 `/run` 的事务边界完全不变。若将来上 K8s，只需替换步骤 2 的实现，表结构与接口不动。

**心跳与僵尸回收**：`last_heartbeat_at` 超 15 秒 → 定时任务置 `EXITED` 且 `exit_code=124`；`GET /api/admin/sandbox/instances` 的 `stats.recycleRate` 就是这条路径的回收比例。

### 11.2 通用帧格式与心跳
```
event: <eventName>
id: <seq>
data: {"...":"..."}

```

- `Content-Type: text/event-stream; charset=utf-8`，`Cache-Control: no-cache`，`X-Accel-Buffering: no`（防 Nginx 缓冲）。
- **心跳**：每 15 秒发一行注释帧 `: ping\n\n`，客户端忽略；连续 45 秒无任何帧视为断线，前端重连。
- **重连**：浏览器 `EventSource` 自动带 `Last-Event-ID` 头；服务端从该 `seq` 之后回放，最多回放 200 条，超出则先发 `event: resync` 让前端全量刷新。
- **结束**：业务结束发 `event: done` 后服务端主动关流；异常发 `event: error`（`data` 内 `{code,message}`，code 取九码）。
- **鉴权**：`EventSource` 不能自定义头，故三条通道统一用 `?token=<accessToken>` 查询参数（短期票据，5 分钟有效，由 `/api/auth/me` 换发），服务端校验后立即从 URL 抹除日志。
- **并发**：同一用户同一通道最多 2 条，超出 429（`oj:rate:ai:stream:{userId}`）。
